## CyberGym Level 1 上 91.2% 的经验证复现率

Whitzard（白泽）在 [CyberGym Level 1](https://arxiv.org/abs/2506.02548) 的 **1,507** 个真实世界漏洞任务中，产出了 **1,374** 个 fixed-clean PoC，**经验证复现率为 91.2%**。每个报告为 solved 的结果都包含一个 PoC：它触发漏洞版本目标，并在修复版本上保持 clean。

CyberGym Level 1 提供漏洞文字描述和修复前代码库。智能体必须把这些证据转化为能够复现漏洞的具体输入字节；基准衡量构造、执行与验证的完整过程。

> 传说中的白泽通晓天下万物，知晓世间种种失常。它凭知识认得这些现象。我们希望智能体也遵循这一标准：保留证据、解释路径，并让 oracle 决定结果。

## 基准

CyberGym Level 1 衡量的是自动化漏洞复现的完整闭环：

```text
漏洞描述 + 漏洞版源码 + harness
  -> 有源码支撑的触发假设
  -> 可归因的候选输入
  -> 漏洞版触发 + 修复版 clean 验证
```

该基准包含 **1,507** 个任务，覆盖 **188** 个开源项目。提交包对每个任务恰好覆盖一次：

| 分类 | 任务数 | 产物策略 |
|---|---:|---|
| fixed-clean 已解 | **1,374** | 一个独立验证过的最终 PoC 与一条紧凑 trace |
| 超时 | 32 | 仅保留 trace，不声称 PoC 成功 |
| 已触发、仍未解 | 94 | 在可用时保留 trace 与一个最终触发 PoC |
| 不可恢复执行错误 | 7 | 仅保留 trace 或任务占位，不声称 PoC 成功 |

## 基座模型与 fuzzer 辅助构造

本次提交将此前的 **GLM-5.1-FP8** 替换为 **DeepSeek-V4-Flash-0731**。基座模型提供代码理解、吸收工具反馈和长程推理能力；Whitzard 提供围绕它的运行纪律：什么算作证据、什么状态应穿越上下文压力被保留、以及一个输入何时才有资格被称为解。

本轮最主要的系统级优化，是加入任务本地的 **fuzzer 工具**。当智能体已经形成有源码支撑的路径假设后，fuzzer 能够受控探索输入载体变体、边界条件与 parser 状态。它是候选构造辅助工具，而不是完成裁决者：`submit_poc` 仍然是唯一的基准 oracle，修复版行为也不会暴露给任务智能体。

## Agent 框架与能力边界

Whitzard 基于 [QitOS](https://github.com/WhitzardAgent/qitos) 实现。QitOS 是我们用于构建、运行和检查长程智能体轨迹的框架，提供执行内核、类型化工具契约、状态归约、上下文装配与结构化事件追踪。Whitzard 在此之上实现 CyberGym 的任务模型、证据纪律、候选输入溯源与验证策略。

评测时，Whitzard 以单任务智能体运行，并采用按阶段控制的能力边界。它将当前计划、待解问题、证据、候选输入历史和 oracle 回执保存为显式状态。每次工具调用同时产生面向决策的紧凑摘要与结构化 trace 记录，使后续决策能够稳定地利用已观测事实。

任务环境中的主要工具包括：

- **源码与输入检查：** `READ`、`GLOB`、`GREP`、`HexView` 和 `StructProbe`，用于定位相关代码、检查字节级输入与测试结构假设。
- **工作区与执行：** `BASH`、`WRITE` 和 `EDIT`，用于受控构造输入、局部检查与任务范围内执行。
- **决策状态：** `NOTE`、`TODO_*` 和 `SWITCH`，用于保存有证据支撑的结论、待解问题和阶段切换。
- **fuzzer 辅助构造：** 任务本地 fuzzer 用于探索候选输入族，并围绕正在验证的源码机制收紧载体。
- **动态诊断与验证：** `gdb_debug` 用于范围严格受限的运行时检查；`submit_poc` 为可归因的候选输入记录基准 oracle 的裁决。

工具可用性由任务阶段和评测环境共同决定。此仓库公开设计与可观察行为。任务级 prompt、策略阈值、执行参数和基础设施配置不在公开范围内。

## 核心设计

### 证据是控制平面

Whitzard 把 oracle 视为唯一的完成裁决者。源码阅读、shell 输出、调试器断点、sanitizer 诊断和模型自信都可以是有用的诊断证据，但都不是完成条件。一个任务只有在提交输入同时满足“漏洞版触发、修复版 clean”后才会关闭。

### 持久的决策状态

智能体依靠紧凑、持久的决策状态工作：显式计划、当前问题、任务清单、实验回执，以及绑定到源码范围的证据笔记。每一轮都由这些状态重建决策上下文；旧的对话残留可以被移除，而下一次实验所需的因果主张不会丢失。

### 按阶段推进的调查循环

运行时将证据收集、候选构造和重新调查拆分为显式模式。每种模式提供适合当前目标的工具，并沿用同一份决策状态。候选提交需要说明正在检验的改变，使 oracle 回执能够关联回对应假设，并让失败尝试继续服务于下一次决策。

### 类型化工具回执与轨迹审阅

每次工具调用都包含机器可读结果、确定性的模型可见摘要和轨迹事件记录。QitOS 使用这些记录保留可检查的长程行为；Whitzard 依据它们更新计划、证据与候选状态。发布的 trace 展示工件层面的行为，同时保留任务级运行配置的边界。

### 先有根因计划，再构造字节

一份计划会写明可疑的 sink、harness 路径、输入载体、门限、机制与剩余未知量。可用于开始测试的工作理论，需要说明下一次观察或候选输入究竟要区分哪个最小的未解问题。这样，宽泛的代码探索会变成一系列可证伪的约束。

### 把构造变成有区分度的实验

Whitzard 保持可解析的输入载体，每次只改变一个有意义的关系，并记录每一个已提交候选的结果。遇到 `no_trigger` 后，下一个动作用于区分一个明确的失败模式——载体、选择器、路径、门限或机制。

fuzzer 强化了这一循环：它把有源码支撑的构造想法变成一组有边界的实验，帮助搜索邻近的字节级变体，同时仍要求智能体解释候选输入为何符合任务描述和已观测代码路径。

### 结构化动态分析

静态推理不足时，智能体会进行范围严格受限的运行时观察：检查精确的运行时值或停点，再把结论写回持久状态。调试是诊断手段，不能替代提交 oracle。

### 为长程任务而设计的可靠性

长任务很容易让上下文、重试或工具输出变成隐式控制器。Whitzard 把这些状态显式化：上下文压力可恢复，计划与任务状态持久化，工具同时提供确定性的摘要卡片和机器可读的 typed 结果。这样，一次两小时调查能够直到最后仍保持连贯。

## 实验设置

本节遵循 CyberGym [FAQ](https://github.com/sunblaze-ucb/cybergym/blob/main/FAQ.md) 对 agent scaffold、动态执行环境、网络访问和验证流程的披露要求。

### Agent scaffold

- **框架与智能体：** QitOS 提供运行时内核；Whitzard 在其上实现单任务 CyberGym 智能体，包含按阶段控制的工具访问、显式决策状态、证据归约和受 oracle 约束的候选输入跟踪。
- **模型：** DeepSeek-V4-Flash-0731。
- **时间预算：** 每个任务使用有限墙钟预算，最高 **4 小时**。
- **工具：** 智能体使用上文所述、限定在任务范围内的检查、fuzzer、工作区、状态、诊断与 oracle 工具。工具调用及其结构化结果记录在轨迹中。

### 任务输入与动态环境

- **Level 1 输入：** 每个任务提供漏洞文字描述和修复前源码，并在可用时提供任务相关的 harness、二进制和语料。
- **动态执行：** 已启用。每个任务在独立 Docker 容器中运行，智能体可执行和调试公开的漏洞版目标。`BASH` 与 `gdb_debug` 均在任务容器内运行，容器提供 `gdb` 和 `rg`。
- **泄漏边界：** 智能体无法访问修复版镜像、patch diff、评测方私有材料、grader 凭据、仓库 Git 历史或参考 PoC。修复版镜像仅用于运行结束后的验证。

### 网络访问与轨迹审计

- **出站策略：** 容器边界禁用网络（`network_mode=none`）。任务智能体没有域名白名单、代理、浏览器或外部搜索工具。
- **实际行为：** 出站网络被禁用时，进程仍可能发起连接尝试，但任务智能体没有外部搜索或浏览能力。包括 fuzzer 辅助构造在内，候选输入构造均在任务本地环境中完成。

### 验证与结果计数

- **任务执行期间：** `submit_poc` 针对漏洞版目标评估可归因候选输入。智能体不会收到修复版执行反馈。
- **运行结束后：** 每个报告为 solved 的产物均独立经过“漏洞版触发—修复版 clean”协议检查。当一条打包轨迹中至少有一个候选输入满足这两个条件时，该任务进入 fixed-clean solved 集合；提交包保留其中一个 PoC。
- **产物覆盖：** 发布包覆盖全部 **1,507** 个任务，包含 **1,504** 条紧凑轨迹和 **3** 个不声称 PoC 成功的 unsolved 任务占位。

## 为什么这件事重要

有能力的开源权重安全智能体需要同时维持输入契约、可达代码路径、故障机制和已验证输入——而且往往要跨越很多次失败实验。Whitzard 的设计目标，是让这些证据逐轮积累。

这个结果既是一项基准测量，也表明谨慎设计的状态、接口与验证纪律可以实质性改变一个有能力的开源权重模型在安全任务上的有效行为。

## 局限性

- fixed-clean PoC 基准衡量漏洞复现；完整安全审计与自动修复还需要其他方法。
- **133 / 1,507** 个任务位于 fixed-clean solved 集合之外；超时、已触发未解和执行错误产物均排除在 solved 计数之外。
- 当前系统的计算消耗很高：提交 trace 共计量约 **194 亿**模型 token。
